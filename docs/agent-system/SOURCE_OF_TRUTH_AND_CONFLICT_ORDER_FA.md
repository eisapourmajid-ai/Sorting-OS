# سلسله‌مراتب مرجع و حل تعارض — SORTING OS

1. دستور/نیازمندی صریح و تازه مالک محصول، تا وقتی با صحت داده، قانون مصوب و محدودیت فنی سازگار باشد.
2. `PROJECT_SPEC.md` و اسناد canonical مالی/عملیاتی داخل `docs/`؛ در امور ریال/تومان، `docs/financial/MONEY_UNIT_POLICY_FA.md` الزام‌آور است.
3. تصمیم‌های `docs/decision-log.md` که وضعیت آنها `Accepted` است و ADRهای پذیرفته‌شده.
4. قراردادهای پوشش، صحت داده، release و وضعیت فعلی در `contracts/`.
5. `reference-inputs/` و نسخه‌های قدیمی فقط به‌عنوان مدرک تاریخی/منبع بررسی؛ اگر با اسناد جاری تعارض داشتند، به‌صورت پیش‌فرض اجرا نشوند.
6. رفتار فعلی کد تنها وقتی مبناست که با سطوح بالاتر تعارض نداشته باشد.
7. پیشنهاد عامل صرفاً `Proposed` است؛ به‌خودی‌خود تصمیم مالک محصول نیست.

## ثبت تعارض

برای هر تعارض یک رکورد شامل فایل‌ها/بخش‌های متعارض، اثر بر داده و حسابداری، گزینه‌ها، پیشنهاد، مالک تصمیم، وضعیت، شناسه نیازمندی و اثر migration در `docs/decision-log.md` اضافه شود. اگر تعارض به مالکیت کالا، صافی، واحد پول، posting، ارزش‌گذاری، قانون مالیاتی یا مانده‌های افتتاحیه مربوط است، قابلیت وابسته تا تأیید `BLOCKED` بماند.

## واژه‌های وضعیت

- `DESIGNED`: قرارداد نوشته شده است؛ کد وجود ندارد.
- `IMPLEMENTED`: کد قابل مشاهده وجود دارد.
- `TESTED`: فرمان آزمون مشخص واقعاً اجرا و نتیجه ثبت شده است.
- `VERIFIED ON TARGET`: روی OS/چاپگر/پیکربندی دقیق هدف آزموده شده است.
- `PARTIAL`, `BLOCKED`, `NOT RUN`, `NOT VERIFIED`: وضعیت‌های معتبرند و شکست محسوب نمی‌شوند؛ مخفی‌کردن آنها ممنوع است.
