# ADR-0001: پلتفرم، اجرای محلی و لایه‌بندی برنامه (Platform and Runtime)

- Status: **Accepted (provisional for Windows 7 packaging — see ADR-0002 open item)**
- Date: 2026-10-19
- Decision owner: مهندس مسئول (Engineering Lead) + مالک محصول
- Related requirements: NFR-OFF-001, NFR-OFF-002, NFR-OFF-003, FIN-MONEY-001..012, FIN-CORE-001..040, RPT-FIN-01..10, RPT-OPS-01..03
- Prompt: 02 (architecture decision and platform matrix)

## Context

Sorting OS یک نرم‌افزار دسکتاپ تک‌کاربره/محدود برای عملیات سورتینگ و حسابداری صافی است. الزام‌های
ثابت محصول:

1. **آفلاین کامل**: بدون CDN، بدون telemetry، بدون login ابری، بدون auto-update اجباری، بدون ارسال
   پنهان داده. کل چرخه کار (ورود محموله → سورتینگ → انبار → فاکتور → دفترکل → گزارش → چاپ → پشتیبان)
   باید روی یک ماشین بدون اینترنت کار کند.
2. **Windows 7 SP1 x64** یکی از سیستم‌عامل‌های هدف است (مبدل اصلی کاربران).
3. **رابط فارسی RTL** و **چاپ** روی پرینترهای A4 حرارتی/لیزری.
4. **صحت مالی**: مبنای پول `integer rial`، `۱ تومان = ۱۰ ریال`، بدون float، بدون گرد‌کردن خاموش.
5. **داده محلی**: یک فایل SQLite روی دیسک کاربر که باید قابل پشتیبان‌گیری، قابل بازیابی و قابل
   انتقال باشد.
6. **هستهٔ مالی موجود** (`desktop/accounting_core.py`) و **هستهٔ عملیاتی موجود**
   (`desktop/database.py`) از قبل کار می‌کنند و ۱۷ تست پایهٔ سبز دارند؛ بازنویسی گستردهٔ آن‌ها
   ریسک از دست رفتن رفتار آزمون‌شده دارد.

## Decision drivers

- صحت و قابلیت ممیزی داده (بازنویسی سند قطعی ممنوع)
- اجرای آفلاین و بدون وابستگی شبکه‌ای
- سازگاری Windows 7 SP1 x64 (و نگهداری چندساله)
- هزینهٔ مهاجرت و ریسک تغییر
- امکان تست headless روی CI لینوکسی (بدون GUI)
- چاپ و RTL
- امکان استفادهٔ چندکاربرهٔ سبک (DEC-007 باز)

## Options considered

### Option A — Python + Tkinter (وضع موجود MVP) — **انتخاب‌شده**

مزایا:
- هستهٔ موجود (حسابداری دوبل + عملیات) بدون بازنویسی حفظ می‌شود؛ ۱۷ تست پایه سبز می‌ماند.
- استاندارد کتابخانه، بدون وابستگی خارجی برای GUI → بسته‌بندی آفلاین ساده.
- Python 3.8+ روی Windows 7 SP1 x64 قابل نصب است (نسخهٔ 3.8.10 آخرین پشتیبانی‌شدهٔ رسمی).
- Tkinter با `ttk` از RTL پشتیبانی نمی‌کند، اما RTL با تنظیم `justify`/`anchor` و چیدمان
  `side="right"` قابل پیاده‌سازی است و مستند UI موجود (`reference-inputs/UI_LAYOUT_THEME_HEADER_SPEC.md`)
  همین را می‌طلبد.

معایب:
- RTL بومی ندارد؛ نیازمند کار دستی در لایهٔ UI.
- Tkinter در محیط سرور/headless قابل تست نیست ⇒ لایهٔ UI باید از لایهٔ سرویس جدا بماند
  (تصمیم کلیدی زیر).
- ظاهر بصری محدود؛ نیازمند قالب‌بندی دستی.

### Option B — Qt (PySide/PyQt) + QML

مزایا: RTL و چیدمان حرفه‌ای، مدل رویداد بهتر.
معایب: وابستگی خارجی سنگین (~۱۵۰MB)، نیازمند بسته‌بندی wheels آفلاین، ریسک سازگاری با
Windows 7 (نسخه‌های قدیمی Qt لازم)، ریسک مجوز (GPL در PySide? PyQt دارای لایسنس تجاری/گنو),
مهاجرت کامل هستهٔ UI. هزینهٔ مهاجرت: بالا؛ ریسک: بالا.

### Option C — Electron/Chromium محلی

معایب: حجم بسیار زیاد، وابستگی به Chromium، Windows 7 پشتیبانی نمی‌شود در نسخه‌های جدید،
نقض صریح الزام offline-first سبک و هزینهٔ نگهداری. رد شد.

### Option D — .NET WPF/WinForms

مزایا: RTL و چاپ بومی، اجرای native.
معایب: بازنویسی کامل هستهٔ Python (حسابداری + عملیات + ۱۷ تست)، مهاجرت پرهزینه و پرریسک در
بازهٔ زمانی پروژه. رد شد (فقط اگر الزام Windows-7-only قطعی شود دوباره بررسی شود).

## Decision

1. **Runtime**: Python 3.8+ (مرجع توسعه: 3.11 در CI) + Tkinter/ttk + SQLite. انتخاب Option A.
2. **لایه‌بندی اجباری چهارگانه** در `desktop/sorting_os/`:
   - `core.py` — سیاست پول (integer rial) و تقویم شمسی آفلاین (تنها منبع حقیقت واحد).
   - `db.py` + `migrations.py` — persistence، تراکنش، migration نسخه‌دار.
   - `services/` — دامنه و سرویس‌ها (اعتبارسنجی، قواعد، posting دفترکل).
   - `ui/` — فقط نمایش/فرم؛ هیچ قاعدهٔ مالی در UI.
   - `reporting` — فقط خواندن از دیتابیس/ledger؛ هیچ محاسبهٔ مالی مستقل در گزارش.
3. **هیچ مسیر runtime** به شبکه، CDN یا سرویس ابری وابسته نباشد. هیچ telemetry.
4. **SQLite محلی** با `PRAGMA foreign_keys=ON`، `busy_timeout`، تراکنش‌های `BEGIN IMMEDIATE` و
   migration نسخه‌دار (schema_meta) — بدون auto-migration از فایل‌های legacy به‌صورت خودکار
   (Prompt 32 به‌صورت صریح و قابل بازبینی).
5. **مقدار پول** همیشه `int` ریال در دیتابیس و در مرز سرویس؛ `Decimal` فقط در نقطهٔ تبدیل ورودی
   کاربر؛ `float` ممنوع. واحد نمایش همیشه در گزارش/چاپ ذکر می‌شود.
6. **تقویم**: موتور شمسی آفلاین داخل `core.py` (بدون API بیرونی) — نسخهٔ فعلی VERIFIED با لنگرها و
   رفت‌وبرگشت ۷۳٬۳۲۳ روزه (بدون خطا) — اما «سازگاری با تقویم رسمی» همچنان به تأیید کسب‌وکار نیاز
   دارد (ADR-0003 در decision-log، باز).
7. **رابط کاربری** در `desktop/sorting_os/ui/app.py` ساخته می‌شود؛ لایهٔ سرویس بدون tkinter قابل
   تست است (همین اصل در `desktop/tests/` رعایت شده: هیچ تستی tkinter را import نمی‌کند).

### چرا این گزینه بر گزینه‌های رقیب برنده شد

هزینهٔ مهاجرت Option B/D چند برابر گسترهٔ تغییر فعلی است، در حالی که الزام‌های اصلی (آفلاین،
Windows 7، چاپ، RTL) با Option A قابل تحقق است. ریسک مالیِ بازنویسی هستهٔ حسابداری در برابر
منفعت صرفاً زیبایی‌شناختیِ UI ناموجه است.

## Consequences

### Positive
- ۱۷ تست پایه حفظ می‌شود؛ هستهٔ مالی بدون بازنویسی توسعه می‌یابد.
- تست‌ها کاملاً headless و سریع‌اند (۱۲۳ تست، ~۴ ثانیه) ⇒ بازخورد سریع در CI.
- بسته‌بندی آفلاین ساده؛ بدون وابستگی خارجی در زمان اجرا.
- جداسازی لایه‌ها اجازه می‌دهد UI بعداً (مثلاً WPF) بدون دست‌زدن به دامنه جایگزین شود.

### Negative / trade-offs
- RTL دستی و ظاهر بصری ساده‌تر.
- UI قابل تست خودکار نیست (در این محیط tkinter نصب نیست ⇒ UI فقط «NOT RUN» قابل گزارش است).
- بسته‌بندی PyInstaller روی W7 باید آزمود شود (خارج از دسترس این محیط).

### Follow-up actions
- Prompt 24: پیاده‌سازی `ui/app.py` با چیدمان RTL و جداسازی کامل از سرویس‌ها.
- Prompt 27: آزمون روی ماشین Windows 7 SP1 x64 (این محیط لینوکسی است ⇒ تا آن زمان
  `NOT VERIFIED ON TARGET OS`).
- Prompt 31: ساخت نصب‌کننده و آزمون روی W7 (با ثبت hash و نسخهٔ Python).
- ADR-0002 (باز): تصمیم نهایی دربارهٔ روش packaging (PyInstaller vs zip + launcher).
