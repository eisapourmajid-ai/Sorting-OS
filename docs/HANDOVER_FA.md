## ۲) اجرای سریع

```bash
cd desktop
python -m unittest discover -s tests -v        # کل آزمون‌ها
python -m sorting_os --doctor                  # سلامت پایگاه داده و نسخهٔ schema
python -m sorting_os --init-db                 # ساخت/ارتقای پایگاه داده
python -m sorting_os                           # اجرای رابط گرافیکی
```

مسیر داده (مستقل از پوشهٔ اجرا):
- Windows: `%LOCALAPPDATA%\SortingOS`
- POSIX: `$XDG_DATA_HOME/sorting-os` یا `~/.local/share/sorting-os`
- بازنویسی: متغیر محیطی `SORTING_OS_HOME`

## ۳) راهنمای کاربر (خلاصه)

1. **اشخاص:** هر طرف حساب یک‌بار ثبت می‌شود؛ تطبیق خودکار بر اساس نام انجام **نمی‌شود** — پیشنهادها
   در صف بازبینی قرار می‌گیرند و تصمیم با انسان است.
2. **محموله و توزین:** وزن ناخالص ≥ وزن خالی؛ وزن خالص محاسبه می‌شود.
3. **سورتینگ:** مجموع خطوط خروجی/ضایعات/افت باید با وزن ورودی برابر باشد؛ در غیر این صورت سند
   رد می‌شود. فقط خطوط «خروجی» به موجودی انبار وارد می‌شوند.
4. **فاکتور:** واحد مبلغ باید صریح باشد (ریال/تومان)؛ مجموع فاکتور = جمع ردیف‌ها؛ فاکتور قطعی
   قابل ویرایش نیست.
5. **دفترکل:** هر posting از یک سند عملیاتی می‌آید و کلید یکتا دارد؛ تکرار ⇒ سند تکراری ساخته
   نمی‌شود. اصلاح فقط با **سند معکوس**.
6. **گزارش‌ها:** همهٔ مانده‌ها از دفترکل قطعی ساخته می‌شوند؛ واحد مبلغ روی هر گزارش درج می‌شود.
7. **دورهٔ مالی:** بستن دوره فقط با backup موفق؛ سند بستن متوازن به ۳۱۰۰ و قفل دوره ایجاد می‌شود.
8. **بانک:** واحد ستون مبلغ باید صریح انتخاب شود؛ فایل تکراری ⇒ بدون ثبت دوباره.
9. **چاپ:** قالب‌ها نسخه‌دار و در پایگاه داده ذخیره می‌شوند؛ واحد همیشه چاپ می‌شود.
10. **صافی و درصد (DEC-017):** درصد صافی در سه سطح تخصیص می‌یابد — **پیش‌فرض** (همیشه قابل
    ویرایش)، **حساب طرف** (هر فرشنده) و **فاکتور** (هر فاکتور نرخ خودش را دارد). ترتیب اعمال:
    فاکتور ← حساب طرف ← پیش‌فرض؛ ورود دستی هنگام محاسبه بالاتر از همه است. ویرایش نرخ فقط
    نسخهٔ تازه می‌سازد و صافی‌های قبلی را تغییر نمی‌دهد. اگر هیچ نرخی نباشد، محاسبه با پیام
    روشن رد می‌شود. تب «صافی و درصد» در صفحهٔ اصلی: `reports/SETTLEMENT_RATE_ASSIGNMENT.md`.

## ۴) راهنمای پشتیبان‌گیری و بازیابی

- **مسیر:** `<data dir>/backups` (فایل‌های `*.sqlite3` + `SHA256SUMS.txt`).
- **ساخت:** `python -m sorting_os --doctor` (سلامت) یا از صفحهٔ پشتیبان‌گیری؛ خروجی شامل
  `sha256` و `schema_version` است.
- **راستی‌آزمایی:** `BackupService.verify(path)` — `PRAGMA integrity_check`، شمارش جدول‌ها و
  نسخهٔ schema را بررسی می‌کند.
- **بازیابی:** `BackupService.restore(path)` — پیش از جایگزینی، یک کپی ایمنی از وضعیت فعلی
  ساخته می‌شود؛ فایل خراب با `ConflictError` رد می‌شود.
- **روش دستی (خط فرمان):** برنامه را ببندید ⇒ از `db/sorting_os.sqlite3` یک کپی بگیرید ⇒ در صورت
  نیاز فایل را جایگزین کنید ⇒ برنامه را باز کنید (migration در صورت نیاز اجرا می‌شود).

## ۵) Runbook ادمین

| وضعیت | اقدام |
|---|---|
| برنامه بالا نمی‌آید | `python -m sorting_os --doctor` ⇒ بررسی integrity و مسیر داده |
| «database is locked» | مطمئن شوید برنامهٔ دیگری باز نیست؛ `busy_timeout` فعال است |
| خطای مهاجرت | نسخهٔ schema قبلی حفظ می‌شود؛ از backup بازیابی و خطا را ثبت کنید |
| حجم پایگاه داده زیاد شد | `VACUUM` فقط در حالت بستهٔ برنامه و پس از backup |
| نیاز به انتقال به رایانهٔ دیگر | پوشهٔ داده را کپی کنید؛ مسیر را با `SORTING_OS_HOME` تنظیم کنید |
| نیاز به بازگشت به نسخهٔ قبلی | نسخهٔ قبلی برنامه + backup قبل از ارتقا |

## ۶) سیاست نسخه و انتشار

- نسخه‌ها به‌صورت `MAJOR.MINOR.PATCH` در `desktop/sorting_os/__init__.py` (`__version__`).
- تغییر schema ⇒ migration جدید در `sorting_os/migrations.py` + `LATEST_SCHEMA_VERSION` + آزمون
  «دیتابیس خالی» و «ارتقا از نسخهٔ قبلی».
- انتشار فقط از طریق PR به `main`؛ `main` مستقیم commit نمی‌شود.
- build: `python3 scripts/build_release.py` ⇒ `dist/SORTING-OS-<version>.zip` + SBOM + checksum.
