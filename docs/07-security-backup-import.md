# امنیت، پشتیبان‌گیری، بازیابی و ورود داده

## 1. مدل تهدید مختصر

دارایی‌های حساس:
- اطلاعات مالی و حساب اشخاص؛
- فاکتورها و محموله‌ها؛
- داده‌های موجودی و صافی؛
- رمزهای کاربران؛
- پایگاه داده و نسخه پشتیبان؛
- سوابق تأیید و تغییرات.

تهدیدهای مورد توجه:
- تغییر اشتباه یا عمدی سند؛
- حذف داده؛
- خرابی دیسک یا پایگاه داده؛
- سرقت فایل پشتیبان؛
- دسترسی غیرمجاز کاربر؛
- دوباره‌ثبت‌شدن عملیات در اثر retry؛
- اجرای ناقص migration؛
- بدافزار یا آسیب‌پذیری سیستم‌عامل قدیمی.

## 2. احراز هویت و مجوز

- رمز عبور به‌صورت plaintext ذخیره نشود.
- برای hash رمز از الگوریتم password-hashing مناسب و salt یکتا استفاده شود.
- سیاست قفل/تأخیر پس از تلاش ناموفق تعیین شود.
- مجوز عملیاتی در Application Service بررسی شود.
- تغییر نقش کاربر در Audit Log ثبت شود.
- مدیر سامانه لزوماً اجازه حذف سابقه مالی نداشته باشد.
- اگر امکان خروج از حساب وجود دارد، قفل خودکار نشست بر اساس سیاست محلی قابل تنظیم باشد.

## 3. Audit Log

حداقل برای این عملیات ثبت شود:
- ایجاد/اصلاح/ابطال سند؛
- تأیید/رد/قطعی‌سازی؛
- تغییر قیمت/نرخ/قواعد مالی؛
- تغییر مجوز و نقش؛
- پشتیبان‌گیری/بازیابی؛
- ورود داده گروهی؛
- اصلاح انبار؛
- ثبت تعدیل وزن؛
- ثبت یا اصلاح صافی.

هر رخداد شامل کاربر، زمان، موجودیت، شناسه، نوع عمل، مقدار قبلی/جدید در حد مجاز، علت و نتیجه باشد. از ذخیره secrets در log خودداری شود.

## 4. پشتیبان‌گیری

### رفتار لازم

- شروع دستی توسط کاربر مجاز.
- اجرای خودکار طبق برنامه محلی.
- مقصد قابل تنظیم.
- نگهداری چند نسل از نسخه‌ها.
- نمایش آخرین نسخه موفق.
- گزارش شکست روشن.
- بررسی وجود فایل و صحت ساختار پشتیبان.
- آزمون بازیابی در محیط مستقل.

### ایمنی پایگاه داده

هنگام تهیه نسخه پشتیبان از SQLite نباید فایل فعال را با روش کپی ساده در شرایطی کپی کرد که ممکن است journal/WAL یا تراکنش فعال باعث نسخه ناسازگار شود. از API/روش رسمی پشتیبان‌گیری مناسب برای نسخه driver انتخاب‌شده استفاده شود و آزمون بازیابی اجرا شود.

### سیاست ذخیره

حداقل یک نسخه خارج از مسیر پایگاه داده اصلی نگه‌داری شود. برای حفاظت در برابر خرابی دیسک، یک نسخه دوره‌ای روی رسانه مستقل لازم است. اگر الزام امنیتی وجود دارد، رمزگذاری backup و مدیریت کلید باید جدا طراحی شود؛ رمزگذاری بدون مسیر بازیابی کلید قابل قبول نیست.

## 5. بازیابی

1. کاربر مجوزدار مقصد/فایل را انتخاب می‌کند.
2. سیستم هویت و سلامت فایل را بررسی می‌کند.
3. پیش از جایگزینی، backup فعلی تهیه می‌شود.
4. بازیابی ابتدا در فایل staging انجام می‌شود.
5. integrity check و migration check انجام می‌شوند.
6. کاربر پیامد بازگردانی به نسخه قدیمی را تأیید می‌کند.
7. پایگاه داده جایگزین/فعال می‌شود.
8. نتیجه و نسخه بازیابی در Audit Log ثبت می‌شوند.

بازیابی نباید بی‌هشدار داده جدیدتر را حذف کند.

## 6. ورود اطلاعات قدیمی

فرمت‌های پایه: CSV و در صورت نیاز Excel از طریق کتابخانه آفلاین و سازگار.

### مراحل Import

1. انتخاب فایل.
2. تشخیص encoding/worksheet.
3. نگاشت ستون‌های منبع به فیلدهای مقصد.
4. preview چند ردیف.
5. اعتبارسنجی قالب و داده.
6. گزارش خطا با شماره ردیف و فیلد.
7. اجرای آزمایشی بدون تغییر دائم.
8. تأیید کاربر.
9. ورود تراکنشی یا دسته‌بندی کنترل‌شده.
10. گزارش تعداد موفق/ردشده/تکراری.

### قواعد Import

- شماره فاکتور کاغذی در فیلد مستقل بماند.
- تاریخ سند با تاریخ ورود داده اشتباه نشود.
- رکوردهای تکراری شناسایی شوند.
- مقدار پول یا وزن با locale مبدا parse و پیش از ذخیره normalize شود.
- ردیف نامعتبر بی‌صدا حذف نشود.
- فایل منبع و fingerprint آن می‌تواند برای سابقه Import ثبت شود، مشروط به سیاست حریم داده.
- داده‌های مالی قدیمی نباید خودکار به سند قطعی حسابداری تبدیل شوند مگر mapping و قواعد تأیید شده باشند.

## 7. فایل‌های پیوست

اگر اسکن فاکتور یا رسید پشتیبانی شود:
- مسیر فایل محلی یا مخزن اسناد تعریف شود؛
- شناسه سند مرتبط نگهداری شود؛
- نوع فایل و اندازه کنترل شود؛
- فایل اجرایی ناشناخته اجرا نشود؛
- backup و restore پیوست‌ها همراه metadata تست شوند.

## 8. Windows 7

Windows 7 از پشتیبانی عمومی خارج شده است. آفلاین‌کردن برنامه از تماس شبکه‌ای می‌کاهد، اما ریسک بدافزار، USB، دسترسی محلی و آسیب‌پذیری سیستم‌عامل را حذف نمی‌کند. دسترسی محدود، پشتیبان مستقل و آزمون بازیابی الزامی‌اند.
