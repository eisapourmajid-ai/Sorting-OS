# برنامه آزمون، معیارهای پذیرش و Definition of Done

## 1. هرم آزمون

### Unit

قواعد مستقل Domain:
- خالص باسکول؛
- تراز وزن سورتینگ؛
- اختلاف و درصد وزن؛
- قیمت ردیف؛
- صافی درصدی/مبلغی؛
- کمیسیون و تخفیف؛
- تخصیص هزینه؛
- تراز بدهکار/بستانکار؛
- انتقال وضعیت؛
- قواعد مجوز.

### Integration

- ذخیره/بازیابی با پایگاه واقعی test؛
- transaction rollback؛
- migration؛
- جلوگیری از posting تکراری؛
- ثبت رویداد انبار؛
- ثبت سند حسابداری؛
- پشتیبان و بازیابی؛
- Import با خطاهای کنترل‌شده.

### UI/End-to-End

- ورود کاربر؛
- ثبت باسکول؛
- ساخت محموله؛
- سورتینگ چندخروجی؛
- انتقال به انبار؛
- خروج چندمحصولی؛
- ثبت وزن گزارش‌شده؛
- هزینه و صافی؛
- تأیید؛
- دریافت/پرداخت؛
- گردش حساب؛
- گزارش و چاپ.

### System/Compatibility

- نصب بدون اینترنت؛
- اجرای واقعی روی Windows 7 SP1 x64؛
- اجرای روی Windows جدیدتر؛
- فونت جایگزین؛
- چاپگر واقعی؛
- خاموش‌بودن شبکه؛
- crash/restart و بررسی صحت داده.

## 2. داده‌های مرزی لازم

- وزن صفر؛
- وزن ناخالص کمتر از وزن خالی؛
- مقدار خیلی بزرگ و کوچک؛
- تعداد اعشار غیرمجاز؛
- مبلغ منفی؛
- مبلغ صفر؛
- درصد خارج از محدوده مصوب؛
- وزن مبنا صفر برای درصد اختلاف؛
- فاکتور بدون ردیف؛
- سند حسابداری نامتوازن؛
- نقش بدون مجوز؛
- تکرار درخواست قطعی‌سازی؛
- قطع برنامه در میانه عملیات؛
- پایگاه داده قفل‌شده؛
- دیسک پر یا مسیر پشتیبان غیرقابل نوشتن.

## 3. سناریوی E2E اجباری

1. ایجاد یک شخص با نقش باغدار و کارفرما.
2. ثبت باسکول ورودی برای محموله.
3. تأیید سند ورودی و ایجاد موجودی اولیه مناسب با مدل مالکیت.
4. ثبت عملیات سورتینگ با حداقل دو درجه محصول و ضایعات.
5. تطبیق تراز وزن.
6. ثبت چند نوع بسته‌بندی.
7. انتقال محصول به محل انبار.
8. ایجاد یک خروج شامل حداقل سه ردیف محصول با وزن‌های مختلف.
9. کاهش موجودی فقط پس از posting مجاز.
10. اتصال سند خروج به پرونده بارفروش.
11. ثبت وزن اعلامی متفاوت برای هر ردیف.
12. ثبت قیمت و هزینه حمل.
13. محاسبه صافی با روش مبلغی و بررسی درصد معادل.
14. رد سند صافی، اصلاح و ارسال مجدد.
15. تأیید و قطعی‌کردن صافی.
16. تسجيل دریافت/پرداخت مستقل.
17. تطبیق مانده حساب.
18. چاپ گزارش A4 و A5.
19. تهیه backup، بازیابی روی محیط test و بررسی صحت رکوردها.

تمام داده‌های نمونه در محیط test باید مشخصاً synthetic باشند و هرگز به پایگاه عملیاتی راه پیدا نکنند.

## 4. معیارهای کمی پیشنهادی

این اهداف باید روی سخت‌افزار مرجع تعریف و ثبت شوند:
- بازشدن داشبورد با پایگاه آزمایشی مرجع: هدف اولیه کمتر از 3 ثانیه.
- جست‌وجوی ساده روی اندازه داده مرجع: هدف اولیه کمتر از 1.5 ثانیه.
- ذخیره سند عادی: هدف اولیه کمتر از 1 ثانیه در سیستم مرجع، جز در عملیات فایل/پشتیبان.
- هیچ عملیات مالی نباید موفق اعلام شود اگر تراکنش ذخیره‌سازی شکست خورده باشد.
- بازیابی backup باید با integrity check موفق همراه باشد.

زمان‌ها اهداف اولیه‌اند و پس از تعیین حجم داده و سخت‌افزار باید بازنگری شوند؛ این اعداد تضمین عملکرد روی تمام رایانه‌ها نیستند.

## 5. تست آفلاین

- ماشین آزمون از اینترنت جدا شود.
- DNS، proxy یا اتصال شبکه نباید برای اجرای اصلی لازم باشد.
- ثبت و چاپ تمام عملیات اصلی آزمایش شود.
- هیچ درخواست خارجی پنهان در log شبکه وجود نداشته باشد، در حد ابزار آزمون قابل مشاهده.
- وقتی API قیمت خاموش است، هیچ درخواست API ارسال نشود.
- در حالت API روشن و قطع اتصال، خطا غیرمسدودکننده باشد و آخرین قیمت محلی با زمان ثبت نمایش داده شود.

## 6. گیت‌های انتشار

### Gate A — دامنه

تصمیم‌های مالی مهم ثبت و تأیید شده‌اند.

### Gate B — Runtime

نمونه تکنولوژی روی Windows 7 و ویندوز جدیدتر نصب و اجرا شده است.

### Gate C — Data integrity

تراکنش، قیود، migration و بازیابی آزمون شده‌اند.

### Gate D — Financial correctness

قواعد صافی، هزینه، موجودی و سند دوبل با مثال‌های مورد تأیید حسابدار آزمون شده‌اند.

### Gate E — UI/Printing

RTL، DPI، گزارش‌ها، A4/A5 و چاپ واقعی بررسی شده‌اند.

### Gate F — Release

installer آفلاین، checksum، notes، backup/restore و گزارش آزمون وجود دارند.

## 7. Definition of Done

قابلیت فقط زمانی Done است که:
- نیازمندی مرتبط به ID مشخص متصل باشد؛
- کد عملیاتی، نه صرفاً mockup، وجود داشته باشد؛
- اعتبارسنجی و کنترل دسترسی اجرا شوند؛
- داده واقعی پایگاه داده مصرف/ثبت شود؛
- آزمون‌های لازم موفق باشند؛
- UI مطابق design system باشد؛
- رفتار آفلاین بررسی شده باشد؛
- مستندات/مهاجرت/گزارش خطا به‌روز باشند؛
- محدودیت‌ها و ریسک‌های باز ثبت شده باشند؛
- یک reviewer مستقل تغییر را بررسی کرده باشد.

## 8. شواهد تحویل

برای هر Release نگه‌دارید:
- نسخه برنامه و commit hash؛
- نسخه dependencyها؛
- نتیجه تست‌ها؛
- پلتفرم‌های آزموده‌شده؛
- hash نصب‌کننده؛
- مراحل نصب/حذف؛
- نتیجه backup/restore؛
- فهرست known issues؛
- تأیید تصمیم‌های تجاری مرتبط.
