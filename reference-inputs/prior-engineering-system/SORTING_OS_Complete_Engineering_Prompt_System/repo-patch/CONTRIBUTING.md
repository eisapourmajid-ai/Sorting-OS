# راهنمای مشارکت در SORTING OS

## پیش از شروع

1. `README.md` و `PROJECT_SPEC.md` را بخوانید.
2. سندهای تخصصی مرتبط را بررسی کنید.
3. تصمیم‌های باز در `docs/decision-log.md` را بررسی کنید.
4. برای قواعد تجاری نامشخص، کد حدسی ننویسید؛ Issue تصمیم باز ایجاد کنید.

## قواعد توسعه

- هر قابلیت باید شناسه نیازمندی یا Issue روشن داشته باشد.
- منطق مالی/انبار در Domain/Application باشد، نه event handler رابط کاربری.
- هر تغییر schema به migration نسخه‌دار و آزمون نیاز دارد.
- سند قطعی با ویرایش مستقیم و بی‌ردپا اصلاح نمی‌شود.
- هر فرمانی که ممکن است دوباره اجرا شود باید idempotency آن بررسی شود.
- وابستگی جدید باید نسخه دقیق، مجوز، footprint، نیازمندی OS و تست آفلاین داشته باشد.
- asset، فونت و آیکون زمان اجرا باید محلی باشند.
- داده واقعی مشتری یا دیتابیس عملیاتی را هرگز در Git ثبت نکنید.
- تست Windows 7 را فقط وقتی ادعا کنید که واقعاً روی محیط هدف اجرا شده باشد.

## کیفیت Pull Request

PR کوچک و متمرکز باشد و شامل شناسه نیازمندی، تغییرات داده، آزمون‌ها، اثر حسابداری/انبار، نتیجه تست آفلاین و ریسک‌ها باشد. برای تغییرهای محاسباتی نمونه ورودی/خروجی و edge case اضافه کنید.

## ثبت تغییرات

تغییر رفتار کاربر، schema، فرمول مالی یا وابستگی باید در مستند مناسب و `CHANGELOG.md` (پس از ایجاد) ثبت شود. تصمیم معماری مهم باید یک ADR داشته باشد.
