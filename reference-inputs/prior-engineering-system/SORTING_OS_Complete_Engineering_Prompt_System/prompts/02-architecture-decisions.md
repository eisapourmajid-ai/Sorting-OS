# فاز 02 — تثبیت معماری و تصمیم‌های باز

**شناسه:** SORTING-OS-P02  
**محدوده:** از دامنه تجاری نامعلوم عبور نکن.

## دستور قابل کپی برای عامل برنامه‌نویس

تو در حال کار روی مخزن واقعی SORTING OS هستی. دستور مادر `MASTER_PROMPT.md` و فایل‌های مرجع `PROJECT_SPEC.md` و مستندات مرتبط را رعایت کن. **فقط همین مرحله را اجرا کن؛ فازهای بعد را آغاز نکن.**

### هدف
اسناد، کد فعلی و تصمیم‌های باز را به یک معماری سازگار تبدیل کن؛ بدون بازنویسی بزرگ یا تصمیم‌گیری پنهانی درباره حسابداری.

### کارهای دقیق
1. قرارداد لایه‌ها را صریح کن: UI/Presentation، Application/use cases، Domain/rules، Persistence/repositories، Infrastructure/printing/import/export/logging؛ نام‌ها را با stack واقعی تطبیق بده.
2. مسیرهای مرجع مدل دامنه را تعریف کن: Party و PartyRole، Product/Grade/Packaging، WeighTicket، Shipment، SortingOperation/Output، InventoryTransaction، Dispatch/DispatchLine، Invoice/InvoiceLine، Expense/Allocation، Settlement، JournalEntry/Line، BankTransaction/Check، AuditLog و ImportBatch.
3. ارتباط‌ها و cardinalityها، کلید داخلی پایدار، شماره نمایشی قابل تنظیم و نگهداری شماره منبع بیرونی را مشخص کن.
4. مدل‌های تجاری ممکن (خدمت سورتینگ برای مالک، خریدوفروش مستقیم، ترکیبی) را از هم جدا نگه دار. ثبت درآمد، بهای کالا، بدهی به مالک، کمیسیون و هزینه تنها با قواعد مصوب انجام شود.
5. تصمیم‌های تک‌رایانه/چندکاربره، SQLite یا گزینه موجود، مسیر فایل دیتابیس، محل backup، تقویم شمسی/میلادی، شماره‌گذاری اسناد، ارز/واحدها و سیاست اصلاح اسناد را از decision log استخراج کن.
6. هر انتخاب فنی مهم را با گزینه‌های درنظرگرفته‌شده، مزایا/معایب، هزینه نگهداری، ریسک Windows 7/آفلاین و وضعیت تأیید به ADR تبدیل کن.
7. ماتریس «نیازمندی → سند → ماژول → آزمون پذیرش» ایجاد کن. موارد نامعلوم را با ID و مالک تصمیم ثبت کن.
8. با کد واقعی مقابله کن؛ معماری روی کاغذ نباید سیستم فعلی را بی‌نیاز از migration، نسخه‌بندی یا سازگاری جلوه دهد.

### خروجی
به‌روزرسانی مدل داده، decision log، ADRها، dependency matrix، نقشه مرزهای ماژول و ماتریس نیازمندی-تست.

### معیار پذیرش
هیچ تعارض دامنه‌ای عمده بدون برچسب باز باقی نماند؛ هیچ مدل موازی برای یک مفهوم ساخته نشود؛ هر تصمیم مهم دلیل و اثر مهاجرت داشته باشد.


## قرارداد مشترک اجرا (الزامی)

این پرامپت را در مخزن واقعی اجرا کن، نه بر اساس حدس. قبل از تغییر، دستور مادر و اسناد مربوط را بخوان؛ `git status`، branch و commit را ثبت کن؛ تغییرات کاربر را دست‌نخورده نگه دار. محدوده این پرامپت تنها محدوده مجاز همین نوبت است. قبل از پیاده‌سازی، فایل‌های محتمل، وابستگی‌ها، خطر داده، اثر UI/مجوز/گزارش، migration و تست را مشخص کن. اگر یکی از قواعد تجاری لازم نامشخص است، به‌جای حدس‌زدن تصمیم باز ثبت کن و بخش وابسته را اجرا نکن. پس از تغییر، build و تست واقعی اجرا کن، diff را مرور کن، اسناد را به‌روز کن و گزارش انتهایی قالب دستور مادر را بده. موفقیت build یا تست، سازگاری Windows 7 یا آفلاین‌بودن را بدون شواهد ادعا نکن. در این نوبت به پرامپت بعدی نرو.
