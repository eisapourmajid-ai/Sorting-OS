# فاز 16 — هسته حسابداری دوبل و دفتر اشخاص

**شناسه:** SORTING-OS-P16  
**محدوده:** فقط قواعد posting تأییدشده را عملیاتی کن.

## دستور قابل کپی برای عامل برنامه‌نویس

تو در حال کار روی مخزن واقعی SORTING OS هستی. دستور مادر `MASTER_PROMPT.md` و فایل‌های مرجع `PROJECT_SPEC.md` و مستندات مرتبط را رعایت کن. **فقط همین مرحله را اجرا کن؛ فازهای بعد را آغاز نکن.**

### هدف
ثبت مالی قابل بازسازی، متوازن و قابل ردیابی بساز؛ نه صرفاً جمع مبالغ فاکتور.

### کارهای دقیق
- Chart of Accounts، JournalEntry، JournalLine، fiscal period در صورت نیاز، source reference و posting status را بر اساس طرح مصوب پیاده کن.
- هر سند قطعی باید مجموع بدهکار و بستانکار برابر داشته باشد؛ قبل از post این قید در service/domain و در صورت امکان لایه persistence اعمال شود.
- قواعد posting جداگانه و versioned برای دریافت، پرداخت، فاکتور، هزینه، موجودی/بهای کالا، کمیسیون و صافی تعریف شوند. مدل خرید مجموعه و مدل خدمات برای مالک کالا نباید یک posting یکسان فرض شوند.
- subledger طرف حساب را از دفتر کل آشتی‌پذیر نگه دار. مانده Party از اسناد قطعی و قواعد مشخص مشتق شود؛ مانده دستی قابل ویرایش نباشد.
- سند posting تکراری با source document + posting key متوقف شود. reversal/correction باید سندی متوازن با پیوند به اصل و علت باشد.
- تاریخ سند و تاریخ قطعی‌سازی جدا باشند؛ قفل بازه زمانی/دوره مالی تنها اگر قانون محصول تصویب شده باشد.
- گزارش گردش حساب، دفتر کل، بدهکار/بستانکار و trial balance تهیه شود. جمع‌ها با محاسبه مستقل reconciliation شوند.
- migration افتتاحیه برای داده تاریخی تنها با ابزار import و ثبت مبنا انجام شود؛ به‌عنوان حقیقت مبهم در فیلد مانده ذخیره نشود.

### معیار پذیرش
تراز دوبل، journal نامتوازن، rollback، posting تکراری، reversal، طرف حساب چندنقشی، مرز تاریخ سند/ثبت و reconciliation دفتر کل/subledger آزموده شوند.


## قرارداد مشترک اجرا (الزامی)

این پرامپت را در مخزن واقعی اجرا کن، نه بر اساس حدس. قبل از تغییر، دستور مادر و اسناد مربوط را بخوان؛ `git status`، branch و commit را ثبت کن؛ تغییرات کاربر را دست‌نخورده نگه دار. محدوده این پرامپت تنها محدوده مجاز همین نوبت است. قبل از پیاده‌سازی، فایل‌های محتمل، وابستگی‌ها، خطر داده، اثر UI/مجوز/گزارش، migration و تست را مشخص کن. اگر یکی از قواعد تجاری لازم نامشخص است، به‌جای حدس‌زدن تصمیم باز ثبت کن و بخش وابسته را اجرا نکن. پس از تغییر، build و تست واقعی اجرا کن، diff را مرور کن، اسناد را به‌روز کن و گزارش انتهایی قالب دستور مادر را بده. موفقیت build یا تست، سازگاری Windows 7 یا آفلاین‌بودن را بدون شواهد ادعا نکن. در این نوبت به پرامپت بعدی نرو.
