## دستور قابل کپی برای عامل برنامه‌نویس

تو در حال کار روی مخزن واقعی SORTING OS هستی. دستور مادر `MASTER_PROMPT.md` و فایل‌های مرجع `PROJECT_SPEC.md` و مستندات مرتبط را رعایت کن. **فقط همین مرحله را اجرا کن؛ فازهای بعد را آغاز نکن.**

### هدف
فرایند پایدار نگهداری نسخه‌ها و اصلاح خطا را تعریف کن.

### کارهای دقیق
- قالب issue با گام‌های بازتولید، نتیجه واقعی/مورد انتظار، نسخه، OS، داده آزمایشی امن و severity استاندارد کن.
- severity را برای ازبین‌رفتن داده، خطای مانده/موجودی، نشت داده، نصب/restore، عملکرد محدود و cosmetic تعریف کن.
- هر bug اصلاحی باید regression test داشته باشد؛ تغییر hotfix با schema migration و backward compatibility بررسی شود.
- سیاست نسخه‌گذاری، changelog، rollback/forward-fix، نگهداری backup پیش از انتشار و انتشار patch آفلاین تعیین شود.
- وابستگی‌ها و مجوزهایشان را دوره‌ای بازبینی کن اما ارتقای یک dependency بدون ماتریس Windows 7 و آزمون آفلاین ممنوع.
- تصمیم‌های کسب‌وکار و درخواست‌های جدید را از bug جدا ثبت کن؛ به‌روزرسانی نیازمندی‌ها باید همزمان روی آزمون‌های پذیرش اثر بگذارد.
- داده تشخیصی export شده را قبل از اشتراک با توسعه‌دهنده برای شناسه ملی، شماره تماس، شماره حساب و اطلاعات محرمانه scrub کن.

### معیار پذیرش
چرخه انتشار بعدی را بتوان بدون یادآوری شفاهی تکرار کرد؛ هر hotfix دارای evidence، changelog و مسیر بازیابی باشد.


## قرارداد مشترک اجرا (الزامی)

این پرامپت را در مخزن واقعی اجرا کن، نه بر اساس حدس. قبل از تغییر، دستور مادر و اسناد مربوط را بخوان؛ `git status`، branch و commit را ثبت کن؛ تغییرات کاربر را دست‌نخورده نگه دار. محدوده این پرامپت تنها محدوده مجاز همین نوبت است. قبل از پیاده‌سازی، فایل‌های محتمل، وابستگی‌ها، خطر داده، اثر UI/مجوز/گزارش، migration و تست را مشخص کن. اگر یکی از قواعد تجاری لازم نامشخص است، به‌جای حدس‌زدن تصمیم باز ثبت کن و بخش وابسته را اجرا نکن. پس از تغییر، build و تست واقعی اجرا کن، diff را مرور کن، اسناد را به‌روز کن و گزارش انتهایی قالب دستور مادر را بده. موفقیت build یا تست، سازگاری Windows 7 یا آفلاین‌بودن را بدون شواهد ادعا نکن. در این نوبت به پرامپت بعدی نرو.
