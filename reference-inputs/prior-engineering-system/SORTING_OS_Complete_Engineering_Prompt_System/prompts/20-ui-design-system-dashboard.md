# فاز 20 — طراحی رابط، هدر، تم و چیدمان شخصی

**شناسه:** SORTING-OS-P20  
**محدوده:** UI باید واقعی، یکپارچه و قابل استفاده با ماوس/صفحه‌کلید باشد.

## دستور قابل کپی برای عامل برنامه‌نویس

تو در حال کار روی مخزن واقعی SORTING OS هستی. دستور مادر `MASTER_PROMPT.md` و فایل‌های مرجع `PROJECT_SPEC.md` و مستندات مرتبط را رعایت کن. **فقط همین مرحله را اجرا کن؛ فازهای بعد را آغاز نکن.**

### هدف
سامانه طراحی قابل استفاده بساز، به‌گونه‌ای که UI عملیات را روشن و کم‌خطا کند، نه اینکه صرفاً تصویری جذاب ایجاد کند.

### قواعد بصری و ساختاری
- فارسی و RTL کامل؛ مسیر خواندن راست‌به‌چپ، اما شماره سند، کد، پلاک، آدرس فایل و عدد direction مستقل داشته باشند.
- تم `Light` و `Dark` کامل در پنجره‌ها، جدول‌ها، فرم‌ها، دیالوگ‌ها، نمودار، toast، tooltip و صفحات مرتبط؛ در Local Settings ذخیره شود.
- هدر: نام صفحه/breadcrumb، جستجوی سراسری، وضعیت محلی/ذخیره‌سازی، صف اعلان و اقدام، سوئیچ تم و منوی کاربر. کنترل تم نباید با خاموش‌کردن برنامه اشتباه شود.
- داشبورد KPIهای قابل انتخاب و قابل مرتب‌سازی محدود، کنترل تراکم Comfortable/Compact، جمع/باز کردن منو و بازگشت به پیش‌فرض داشته باشد؛ این تنظیمات نباید داده تجاری را تغییر دهند.
- طراحی واکنش‌گرا در محدوده اندازه پنجره دسکتاپ، scaling DPI و رزولوشن پایین؛ فرم‌ها قابل استفاده با Tab/Enter/Esc و focus قابل مشاهده داشته باشند.
- فرم‌های پرتکرار با keyboard-first design، autocomplete و جستجوی سریع، حفظ draft در خطای زیرساخت و پیام validation کنار فیلد باشند.
- رنگ فقط معنای عملیاتی پایدار داشته باشد؛ وضعیت صرفاً با رنگ نشان داده نشود؛ کنتراست و اندازه متن مناسب باشد.
- آیکون، فونت، نمودار و asset از فایل محلی بیاید؛ هیچ asset remote.
- تمام دکمه‌ها یا عملکرد واقعی داشته باشند یا به‌وضوح disabled/coming soon باشند و در محیط production گمراه‌کننده نباشند.

### معیار پذیرش
تست UI روی RTL، متون طولانی، عدد mixed-direction، DPI scaling، navigation با صفحه‌کلید، تم روشن/تیره، restart persistence، error/empty/loading states و عدم تغییر داده با تغییر ظاهر.


## قرارداد مشترک اجرا (الزامی)

این پرامپت را در مخزن واقعی اجرا کن، نه بر اساس حدس. قبل از تغییر، دستور مادر و اسناد مربوط را بخوان؛ `git status`، branch و commit را ثبت کن؛ تغییرات کاربر را دست‌نخورده نگه دار. محدوده این پرامپت تنها محدوده مجاز همین نوبت است. قبل از پیاده‌سازی، فایل‌های محتمل، وابستگی‌ها، خطر داده، اثر UI/مجوز/گزارش، migration و تست را مشخص کن. اگر یکی از قواعد تجاری لازم نامشخص است، به‌جای حدس‌زدن تصمیم باز ثبت کن و بخش وابسته را اجرا نکن. پس از تغییر، build و تست واقعی اجرا کن، diff را مرور کن، اسناد را به‌روز کن و گزارش انتهایی قالب دستور مادر را بده. موفقیت build یا تست، سازگاری Windows 7 یا آفلاین‌بودن را بدون شواهد ادعا نکن. در این نوبت به پرامپت بعدی نرو.
