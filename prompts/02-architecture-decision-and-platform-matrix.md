# Prompt 02 — تصمیم معماری و ماتریس سازگاری

**English label:** Architecture decision and platform matrix
**گروه:** آغاز و معماری
**حالت اجرا:** توسعه محدود همراه آزمون

## تصمیم‌های اجباری برای هسته مالی
معماری باید مبنای integer rial، واحد ورودی جدا از واحد نمایش، `Decimal` در مرز تبدیل، و محدودیت‌های SQLite محلی را حفظ کند. هر پیشنهاد برای decimal/float money، auto-sync، posting مستقیم از UI یا migration خودکار legacy نیازمند ADR و تست داده است. لایه‌های UI، domain/accounting service، persistence و report query جدا بمانند.


## هدف دقیق
معماری واقعی را با الزامات offline-first، Windows 7 SP1 x64، فارسی RTL، چاپ و نگهداری محلی مقایسه کن. وضعیت MVP فعلی Python/Tkinter را با اسناد هر معماری دیگر تطبیق بده؛ اختلاف را پنهان نکن. قبل از تغییر فناوری، ADR بساز، هزینه مهاجرت و ریسک را شرح بده و تا وقتی شواهد سازگاری و تصمیم مصوب نیست بازنویسی گسترده نکن.

## قواعد ثابت این عامل در تمام مراحل
1. ابتدا دستور مادر `MASTER_PROMPT_FOR_AGENT_FA.md` و `docs/` مرجع را بخوان. دستور این مرحله به معنی نادیده‌گرفتن نیازمندی‌های پایدار نیست.
2. روی شاخهٔ feature و یک تغییر محدود کار کن. هرگز force-push، reset مخرب، حذف داده کاربر یا commit مستقیم به `main` انجام نده. پیش از تغییر، status و diff را ببین.
3. چیزی را به‌عنوان اجراشده گزارش نکن مگر فرمان واقعی را اجرا کرده و نتیجه‌اش را مشاهده کرده باشی. «طراحی شده»، «پیاده‌سازی شده»، «آزمون شده» و «تأیید روی سیستم هدف» چهار حالت متفاوت‌اند.
4. هیچ مانده مالی یا موجودی را با ویرایش مستقیم عدد به‌روزرسانی نکن. حرکت‌ها از اسناد معتبر، migration و transaction ساخته شوند. سند قطعی حذف/بازنویسی بی‌ردپا نشود.
5. فایل‌ها/داده‌های حساس، شناسه‌های واقعی، رمز، token، export بانکی و دیتابیس عملیاتی را به git یا گزارش عمومی اضافه نکن. برای test از داده مصنوعی یا anonymized استفاده کن.
6. از فرض کردن قانون مالی، نرخ صافی، تلورانس، روش ارزش‌گذاری یا تقویم عملیاتی خودداری کن. مورد حل‌نشده را با اثر و گزینه‌ها در `docs/decision-log.md` ثبت و تا روشن‌شدن قاعده، feature وابسته را BLOCKED/feature-flagged نگه دار.
7. در import، قبل از commit preview/dry-run، row-level errors و idempotency الزامی است. شباهت اسم تنها دلیل ادغام خودکار اشخاص نیست.
8. همه مسیرهای مهم باید آفلاین کار کنند. هیچ CDN/login ابری/telemetry/auto-update اجباری و ارسال پنهان داده مجاز نیست. سازگاری Windows 7 فقط با آزمون واقعی همان سیستم ادعا شود.
9. کد UI، دامنه، persistence و گزارش را تا حد ممکن جدا و قابل‌آزمون نگه دار. وابستگی جدید باید با معماری و مجوز سازگار باشد و در محیط آفلاین بسته‌بندی شود.
10. پس از تغییر، تست‌های مرتبط و مجموعه موجود را اجرا کن؛ diff و وضعیت git را مرور کن؛ فقط فایل‌های مرتبط commit شوند. اگر تست به علت محیط قابل اجرا نیست، صریحاً NOT RUN ثبت کن و موفقیت نساز.
11. تغییر ساختار داده باید migration نسخه‌دار، مسیر دیتابیس خالی و ارتقا از نسخه قبلی، backup/recovery و regression tests داشته باشد.
12. در پایان، گزارش اجباری بده: خلاصه، فایل‌های تغییرکرده، دلیل معماری، requirement IDs، تست‌ها و خروجی واقعی، build وضعیت، محدودیت‌ها، تصمیم‌های باز، commit SHA/PR و فرمان مرحله بعد.


## چک‌لیست اجرایی مخصوص این مرحله
- [ ] وضعیت branch، commit پایه، worktree و تغییرات کاربر را بررسی کن؛ هیچ تغییر ناشناخته‌ای را overwrite نکن.
- [ ] requirementهای مرتبط را به شناسه‌های واقعی در traceability وصل کن. اگر شناسه وجود ندارد، پیش از توسعه اضافه‌اش کن.
- [ ] طرح کوچک و قابل بازبینی بساز و فایل‌های موجود را ترجیح بده؛ یک معماری موازی/مدل داده تکراری ایجاد نکن.
- [ ] مسیر happy-path و حداقل سه failure/edge case را مشخص کن.
- [ ] اعتبارسنجی در لایه دامنه/سرویس انجام شود؛ UI validation به‌تنهایی کافی نیست.
- [ ] آثار بر داده، migration، audit، مجوز، import/export، چاپ، آفلاین و گزارش‌ها را بررسی کن.
- [ ] اگر مرحله به تصمیم باز وابسته است، مرز امن بساز و feature را بی‌سر و صدا با قانون جعلی کامل جلو نبر.
- [ ] آزمون هدفمند بساز یا اصلاح کن؛ تست ناموفق را پنهان نکن.
- [ ] یک diff کوچک و گزارش شواهد آماده کن؛ اگر بیش از یک bounded change لازم است، آن را به زیرفازهای مستقل تقسیم کن.

## توقف اجباری / گیت عبور
- اگر مخزن/source/داده مورد نیاز در دسترس نیست: `BLOCKED`؛ مسیر جایگزین را پیشنهاد کن، اما وجود آن را فرض نکن.
- اگر build/test شکست خورد: `FAILED` همراه خلاصه قابل بازتولید؛ تا رفع یا پذیرش ریسک مصوب، مرحله بعد وابسته را آغاز نکن.
- اگر تست مربوط به محیط هدف اجرا نشده: `NOT VERIFIED ON TARGET OS`؛ از عبارت «سازگار است» استفاده نکن.
- پایان موفق زمانی است که خروجی و شواهد فوق ثبت شده باشند، نه صرفاً وقتی کد نوشته شد.

## قالب گزارش پایان
`STATUS: PASS | PARTIAL | BLOCKED | FAIL`

1. **خلاصه:** چه چیزی واقعاً انجام شد؟
2. **فایل‌ها:** مسیر و دلیل هر تغییر.
3. **Req IDs:** شناسه‌های پوشش داده‌شده و وضعیت آنها.
4. **تست‌ها:** فرمان دقیق و نتیجه واقعی، شامل موارد اجرا نشده.
5. **ریسک/تصمیم باز:** اثر و مالک تصمیم.
6. **Git:** branch، commit SHA، diff/PR.
7. **مرحله بعد:** شماره پرامپت بعدی فقط اگر گیت پاس شده باشد.
